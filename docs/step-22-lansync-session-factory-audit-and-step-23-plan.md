# LanSyncSessionFactory Audit and Step 23 Plan

## Executive assessment

`LanSyncSessionFactory.kt` implements the core cryptographic session-establishment sequence correctly at the protocol level. It creates an in-memory P-256 ephemeral key, signs the canonical session-init descriptor with the Android Keystore identity key, sends the signed request to the Hub, verifies the returned identity bindings and Ed25519 Hub signature, reconstructs the transcript hash, derives ECDH/HKDF session keys, verifies the transcript-bound Hub key-confirmation MAC, validates the four-byte nonce prefix, and constructs a directional AES-GCM `LanSyncHttpSession`.

The factory is therefore a strong **cryptographic foundation**, but it is not yet a production-usable Android sync path. The most important blocker is transport incompatibility: the factory posts to `http://.../sync/session-init`, the desktop Hub currently uses an HTTP server, while `AndroidManifest.xml` explicitly sets `android:usesCleartextTraffic="false"` and the application targets SDK 36. The Android client will not be able to connect to the current Hub endpoint unless the transport is changed to authenticated TLS or the cleartext policy is deliberately relaxed. Authenticated TLS is the recommended solution even though the session frames are already encrypted, because it protects endpoint metadata and prevents downgrade, redirect, and active-network manipulation.

## Recommended next development step: Step 23

The next step should be **Step 23 — Android production sync integration and secure LAN transport hardening**. It should not add another cryptographic primitive first. The remaining risk is that the secure session factory is currently isolated from the Android application and cannot connect to the Hub under the current cleartext policy.

The implementation should proceed in the following order. First, establish the transport contract by converting the Hub LAN server to HTTPS or introducing an authenticated TLS front end, provisioning a Hub certificate during local setup, and pinning or otherwise explicitly trusting that certificate on Android. The signed Ed25519 Hub grant remains the application-level trust anchor; TLS adds endpoint and metadata protection rather than replacing grant verification.

Second, add encrypted Room persistence for a single active Android connection profile. The profile should include the organization ID, enrollment ID, device ID, user ID, policy version, allowed scopes, Hub host and port, transport mode, Hub trust-anchor identity/version, trusted Hub public key or certificate material, and enrollment validity state. The profile must be written only after successful enrollment acknowledgment and must be revocable or replaceable by an administrator-approved flow.

Third, open the encrypted Room database during `EliteApplication.onCreate()`, load the active profile, and construct a `SecureSessionTransport` whose `openSession()` creates `LanSyncSessionFactory` with the persisted policy, trust material, and endpoint. The application should fail closed when the database, enrollment profile, or trust anchor is missing rather than silently creating an unauthenticated transport.

Fourth, refactor `SecureSyncCoordinator` into a bidirectional synchronization orchestrator. Each run should open one session, request deltas for every allowed scope using the stored cursor, pass the exact request nonce into delta verification, apply verified responses transactionally, and then drain the local outbox. A run with no pending outbox events must still perform pull synchronization. Session closure must occur in `finally`, and expiry or authentication failures should invalidate the profile or trigger a controlled re-enrollment path rather than indefinite retries.

## Acceptance criteria

Step 23 should be considered complete only when a synthetic Android profile can be loaded from encrypted Room, an Android `SecureSessionTransport` can open a session against the secured Hub endpoint, and a WorkManager run can pull a signed delta even when the local outbox is empty. The test must demonstrate that the response nonce matches the exact request nonce, the cursor advances only after successful verification and application, and an expired or revoked profile fails closed.

The final end-to-end test should cover both directions in one run: a Hub-side synthetic appointment change must appear in Android sync metadata, and a synthetic Android outbox operation must receive the expected encrypted acknowledgment. The test data must remain synthetic and must not contain real patient information.

## Files likely to change in Step 23

The primary Android changes will be in `EliteApplication.kt`, `SecureSyncCoordinator.kt`, `VerifiedDeltaSynchronizer.kt`, `LanSyncHttpSession.kt`, `LanSyncSessionFactory.kt`, `EliteDatabase.kt`, `SyncDao.kt`, `SyncWorker.kt`, and new connection-profile/policy repository files. The desktop changes will be in the LAN server startup and certificate configuration. New Android unit tests should cover the factory and orchestration boundaries, while the existing TypeScript loopback test should be extended to exercise the transport certificate/profile contract where practical.
