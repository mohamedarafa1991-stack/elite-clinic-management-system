# Step 14 — National FHIR Profile Bundles and Automated ZIP Verification

## Purpose

Step 14 extends the signed ZIP export workflow with **offline, installable FHIR R4 conformance profile bundles** and an automated end-to-end verification test. A profile bundle can represent a clinic-specific, partner-specific, or national implementation-guide constraint set. The selected bundle is validated before it becomes active, copied into each FHIR ZIP package, hashed, and covered by the package signature.

The application does not claim that the built-in Elite Clinic profile is an official Egyptian national implementation guide. A public-source review did not identify a verified official Egyptian FHIR R4 implementation guide suitable for embedding as authoritative conformance material. The software therefore provides the import and provenance mechanism without fabricating a national standard. When the clinic receives an official national or partner IG package, an administrator can install its normalized profile bundle through the organization-settings panel.

## Profile bundle format

A profile bundle is a versioned JSON document with a stable identifier, jurisdiction, publisher, FHIR version, and one or more resource constraints.

```json
{
  "id": "national-eg-r4",
  "displayName": "Example National Patient Document R4",
  "jurisdiction": "EG",
  "version": "2026.1.0",
  "fhirVersion": "R4",
  "publisher": "Example Standards Authority",
  "sourceUri": "https://example.invalid/fhir/ig",
  "profiles": [
    {
      "resourceType": "Bundle",
      "canonicalUrl": "https://example.invalid/fhir/StructureDefinition/document-bundle",
      "requiredPaths": ["type", "timestamp", "identifier", "entry"],
      "fixedValues": { "type": "document" }
    },
    {
      "resourceType": "Patient",
      "canonicalUrl": "https://example.invalid/fhir/StructureDefinition/patient",
      "requiredPaths": ["id", "name"],
      "fixedValues": {}
    }
  ]
}
```

The supported constraint subset is intentionally explicit and deterministic. `requiredPaths` uses simple dotted JSON paths such as `identifier.value`; `fixedValues` supports string, number, and boolean primitive values. The application validates the bundle schema before installation and stores a SHA-256 hash of its canonical JSON representation.

> This profile-bundle format is an **offline application manifest for a constrained validator**. It is not a replacement for the full HL7 `StructureDefinition`, terminology, slicing, cardinality, invariant, and extension machinery defined by FHIR implementation guides.

The design follows the FHIR R4 concepts of [ImplementationGuide][1] and [StructureDefinition][2]. A later enhancement can import a complete packaged IG publisher output and map its computable StructureDefinitions and value sets into the same trust and provenance workflow.

## Installation and selection

Only an administrator with the existing module-management capability can install or replace a profile bundle. Installation creates or updates a row in the encrypted local `fhir_profile_bundles` table and records a successful audit event. Duplicate bundle IDs are updated rather than duplicated. Disabled or missing bundles cannot be selected as the active export profile.

The organization-settings panel provides the following workflow:

1. Load organization settings and the currently available built-in or installed bundles.
2. Paste a validated profile-bundle JSON document and install it.
3. Select the active bundle from the profile list.
4. Save the organization settings.
5. Run FHIR preflight validation before creating a ZIP package.

If a custom profile requires a field excluded by the selected redaction policy, validation fails and ZIP creation is blocked. This prevents a package from claiming conformance while omitting a nationally required element.

The built-in `elite-clinic-r4` bundle remains available as a safe local default. It validates the resources currently generated by Elite Clinic and requires the document Bundle metadata and the minimum resource fields already enforced by the base validator.

## ZIP provenance

For FHIR ZIP packages, the archive contains a canonical JSON member named `{profile-id}.fhir-profile.json`. The manifest records:

| Manifest field                     | Meaning                                             |
| ---------------------------------- | --------------------------------------------------- |
| `fhirProfileBundleId`              | Stable selected bundle identifier                   |
| `fhirProfileBundleHash`            | SHA-256 hash of the canonical profile-bundle member |
| `fhirValidation.profileBundleId`   | Bundle used by the validator                        |
| `fhirValidation.profileBundleHash` | Canonical hash recorded in the validation result    |
| `fhirValidation.profileIds`        | Base R4 and custom canonical profile identifiers    |

The profile member is included in the signed member-hash map and the package-content hash. The in-process verifier and dependency-free external verifier both reject a FHIR ZIP package when the profile member is absent, changed, or inconsistent with the manifest hash.

This makes the package self-describing and offline-verifiable. A recipient does not need access to the clinic database to know which conformance constraints were selected for the export. The recipient still needs to decide whether the publisher, source URI, and profile version are trusted for the intended national or partner exchange.

## Automated integration coverage

The auth integration test now creates a synthetic signed ZIP using a generated Ed25519 key, writes it to a temporary directory, invokes `tools/verify-export.mjs` as a child process, parses the JSON result, and asserts `verified: true`. It then creates a tampered ZIP and asserts that the external verifier exits nonzero. Finally, it supplies a trusted revocation ledger and asserts that the previously valid ZIP is rejected without changing the archive bytes.

The same test installs a synthetic national profile bundle, selects it through organization settings, validates a clinical FHIR export against it, proves that a minimal redaction fails when the selected profile requires `Patient.name`, and verifies that the selected profile ID and hash are carried into the signed ZIP manifest.
