# Elite Clinic Workstation and Device Validation Matrix

**Prepared by:** Manus AI
**Clinic:** Elite Clinic / ايليت, Cairo, Egypt
**Scope:** Windows Hub, Android client, secure LAN synchronization, recovery, and release operations
**Data policy:** Synthetic records only until production sign-off

## Purpose

This matrix converts the remaining release blockers into observable tests. It separates checks that can run in the repository workspace from checks that require a Windows workstation, a supported Android device, a second Android device for concurrency, or controlled removable media. A source-level assertion or a passing JVM test is not accepted as evidence for a physical behavior such as SQLCipher startup, screenshot protection, process death, or LAN recovery.

The local-first deployment model requires the Windows Hub to remain useful without internet or LAN, while Android devices synchronize only through the approved encrypted LAN session.[1] The Android release pipeline already validates compilation, lint, APK structure, static security policy, migrations, synchronization scopes, and doctor-document source boundaries.[2] The physical matrix below begins where those sandbox checks end.

## Evidence status vocabulary

| Status           | Meaning                                                                                                               | Release interpretation                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `passed`         | The named test was executed with the required environment and the evidence is archived.                               | The gate may be considered satisfied for the recorded build and device combination. |
| `failed`         | The test executed and the observed result violated the pass criteria.                                                 | Release is blocked until the defect is triaged and retested.                        |
| `blocked`        | The test could not execute because a required environment, device, credential, or approved procedure was unavailable. | The gate remains open; do not convert it to `passed` based on source inspection.    |
| `not-applicable` | The clinic explicitly approved that the test does not apply to the release scope.                                     | Record the approving Admin and reason.                                              |
| `pending`        | A planned test has not yet been attempted.                                                                            | It remains a release blocker.                                                       |

## Environment inventory

Every evidence record must identify the exact software and hardware used. The minimum inventory is the Git commit, Windows Hub build or installer checksum, Android APK checksum, database schema/migration version, Android model and API level, Android security patch level, device enrollment identifier, certificate/trust-anchor version, and the operator/Admin who performed the test. No personal device identifier should be copied into a report unless the clinic has approved it; use a sanitized device label where possible.

| Environment            | Minimum required setup                                                                                                                     | Evidence fields                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| Repository workspace   | Clean checkout, Node 22.13+, pnpm 10.14.0, and the repository’s package lock state.                                                        | Commit, branch, Node version, pnpm version, command output, report hash.                                 |
| Windows Hub            | Windows 10 and Windows 11 test machines, packaged application, local firewall policy, and the production-like encrypted key-provider path. | OS build, installer filename/checksum, app version, database path policy, TLS certificate label, result. |
| Android floor device   | Android 10/API 29-class device with supported storage and camera-optional behavior.                                                        | Manufacturer/model label, API level, security patch, APK checksum, enrollment label, result.             |
| Android current device | Current clinic-supported Android device with modern API and security patch.                                                                | Manufacturer/model label, API level, security patch, APK checksum, enrollment label, result.             |
| Two-device LAN         | Windows Hub plus two Android devices on an isolated synthetic-data LAN with no internet dependency.                                        | Hub label, device labels, LAN topology label, trust-anchor version, scenario report.                     |
| Recovery media         | Admin-controlled encrypted USB media with a second verified copy during the pilot.                                                         | Media label, backup manifest hash, operator, restore target, retention decision.                         |

## Two-device LAN and recovery sequence

The recommended order is to establish the Hub with synthetic data, enroll both Android devices, verify the correct and wrong trust-anchor behavior, disconnect LAN and internet, perform independent offline operations, reconnect one device at a time, stop and restart the Hub during an in-flight retry, then complete the second-device fairness and conflict cases. Only after synchronization health is green should the document-vault and billing-summary cases be run. The operator should preserve the sequence rather than testing each feature in isolation because the release risk is concentrated at the boundaries between enrollment, encrypted transport, local storage, recovery, and role policy.

A physical run must produce a structured JSON record rather than relying on verbal confirmation. The record template is stored at `docs/templates/physical-device-validation-record.json`; the checklist is stored at `docs/templates/physical-device-validation-checklist.md`. Every unexecuted case must remain `pending` or `blocked`, never `passed`.

## Release decision rule

Clinical production remains blocked if any P0/P1 security or data-integrity case is `failed`, if a required case is `pending` or `blocked`, if the backup cannot be restored with the approved key, if a physical device writes doctor-document content outside the approved Android mechanisms, or if the signed installer/APK lifecycle has not been observed on the intended platforms. The local validation harness may report green local gates and pending physical gates simultaneously; that is the expected state before workstation access is available.
